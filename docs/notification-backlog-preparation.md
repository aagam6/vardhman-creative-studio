# Explicit backlog preparation and standalone combined-pass notification

This adds no worker, automatic activation, schema migration or legacy-queue processing. The existing notification dispatch, owner, CSRF/Origin, provider validation and rate guards remain required. Default dispatch stays OFF. Existing bookings, attendees, passes, capabilities, legacy queues, Trash and reminders are never rewritten by these operations.

`POST /admin/notification-outbox/prepare-subject` accepts only an exact purpose and subject ID. Supported purposes are missing bilingual confirmation, waiting acknowledgement, standalone pass link and initial Attendance. The shared `notification-prepare` ten/minute bucket covers this endpoint and existing intent preparation together. The foreground UI accepts at most 20 exact IDs and spaces preparation requests by 6.5 seconds. Preparation never calls provider submission, never starts a worker, never resumes after refresh and stops on an unconfirmed response.

Attendance takes one confirmed booking ID, expands related contact/event bookings using the existing server gate, excludes unresolved duplicate and repeated-name holds and answered contacts, and reuses the unique initial review scope. An already-issued link is never replaced. If its encrypted outbox exists it is reused; if a hash exists without an encrypted outbox, original secure escrow is required and preparation blocks. For a previously unissued link, token hash/expiry and AES-GCM encrypted outbox commit in one transaction. A failed preparation rolls the token back. Raw tokens never leave this operation or appear in responses/audits.

Standalone `pass_link` uses the existing `ayambil_pass_ready` template, exact six BODY positions, `en`, approved Utility status, a unique provider UUID, healthy configured channel and the existing reviewed BODY policy. Provider-supplied components must match; no omitted-definition fallback without the existing explicit operator policy. It sends one canonical booking-level combined URL, derived from the unchanged existing capability scheme, containing all currently valid passes. It does not repeat a confirmation or add legacy rows. Any prior attempted/provider-referenced legacy pass message or submitted/uncertain bilingual admission CTA blocks this path. Its durable dedup unit is booking + pass_link + initial, not attendee.

Confirmed admission/pass purposes now also check unresolved duplicate/repeated-name holds when preparing, claiming and immediately before submission, under the event lock. Attendance keeps its existing broader eligibility gate. These are communication holds only: no cancellation, pass mutation or automatic duplicate decision.

Every purpose, including waiting acknowledgement and duplicate verification, rechecks its source after claiming and immediately before provider submission. Waiting explicitly requires its saved WhatsApp consent to remain true (registration already requires consent). A consent revocation, approval transition or saved family response blocks the final boundary. Source/event locks use the same event-first order for preparation and dispatch. This does not make an external provider call atomic with a subsequent family/admin action, and does not permit retry of an attempted/uncertain record.

Local evidence: 55 disposable MySQL assertions with two in-memory mock submissions, protected booking/pass/capability/legacy rows unchanged; concurrent preparation/submission dedup; six-pass combined download; initial-link rollback; existing-link preservation; answered exclusion; late holds before claim and after claim. Existing Attendance regression: 37 assertions, one in-memory mock submission, zero actual provider/network calls. API tests cover auth/CSRF/Origin, no recipient override and shared preparation limits. Provider contract tests reject bad UUID/language/category/status/BODY/mapping/channel and validate the exact existing pass payload. None of this constitutes live delivery evidence.
